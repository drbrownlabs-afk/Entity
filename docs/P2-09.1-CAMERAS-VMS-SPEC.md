# P2-09.1 — Cámaras IP virtuales y VMS externo

**Estado:** especificación acordada; implementación pendiente.  
**Fecha:** 2026-11-09.  
**Contexto:** P2-09 de ENTITY, simulación de instalación comercial en coworking.

## Decisión
Se utilizará una **computadora adicional como infraestructura simulada del cliente** para simplificar la instalación del sistema de videovigilancia. **ENTITY Core continúa en GitHub Codespaces**; no se traslada a la computadora del cliente.

## Flujo
1. **PlayCanvas:** el coworking 3D renderiza imágenes desde **ocho cámaras virtuales**. Se configuran con parámetros equivalentes a cámaras IP comerciales (óptica/campo visual, resolución, FPS, formato y calidad). Las ubicaciones y cobertura se calibrarán contra la escena; no se consideran definitivas.
2. **Captura y codificación:** un puente convierte cada vista renderizada en vídeo continuo, preferentemente H.264, con timestamps. Configurar las propiedades visuales en PlayCanvas no basta para generar una cámara IP.
3. **Emulador de cámaras IP:** ocho dispositivos lógicos CAM-01…CAM-08 exponen los streams mediante **RTSP** y, cuando se implemente, los servicios **ONVIF**. Cada dispositivo conserva identidad, configuración y URI de vídeo coherentes. No se presupone compatibilidad completa con firmware propietario Hikvision.
4. **VMS real en computadora de laboratorio:** un software comercial de videovigilancia (candidato: **Agent DVR**) recibe y administra estas fuentes como cámaras IP, permitiendo visualización y, según configuración, grabación y gestión. La compatibilidad concreta se prueba antes de declararla operativa.
5. **ENTITY Connector → percepción → Core:** ENTITY se integra como servicio externo mediante API del VMS y/o acceso autorizado al vídeo y eventos. El pipeline real de detección, tracking y reidentificación multicámara produce observaciones; el Core entidadiza, actualiza estado, relaciones, eventos y memoria.

## Restricciones esenciales
- **El VMS pertenece conceptualmente al cliente, no a ENTITY.** ENTITY es SaaS externo. En producción se conectará a cámaras, NVR/VMS y sistemas preexistentes de cada instalación.
- **ENTITY no recibe datos privilegiados de PlayCanvas:** IDs internos de personajes, coordenadas, trayectorias y ground truth quedan aislados para evaluación; la percepción solo consume imágenes y eventos de integraciones legítimas.
- La simulación debe permitir sustituir cámaras virtuales por cámaras físicas sin cambiar el contrato de entrada del sistema de percepción.
- No instalar ENTITY Core en el PC del cliente. Un Edge local, si se necesita, solo realiza procesamiento de sensores y comunica observaciones hacia el SaaS.
- No confundir emulación ONVIF/RTSP con firmware real de fabricante. La elección definitiva del VMS, emulador y perfiles de cámara se hará por prueba de compatibilidad.

## Stack candidato de laboratorio
**PlayCanvas → captura/encoder → streams RTSP + emulación ONVIF → Agent DVR (PC de laboratorio) → conector externo ENTITY → percepción → ENTITY Core (Codespaces).**

MediaMTX es candidato para transporte/publicación de streams; el emulador ONVIF es candidato para exponer dispositivos. Son componentes por integrar y medir, no instalaciones ya comprobadas.

## Plan de validación
1. Una cámara: render → H.264 → RTSP → VMS, vídeo estable y con latencia medida.
2. Dos cámaras: identidades y streams independientes; seguimiento al cruzar vistas.
3. Ocho cámaras: cobertura calibrada, rendimiento medido, gestión desde VMS.
4. Conector ENTITY: acceso al vídeo/eventos desde el VMS sin consultar estado interno del simulador.
5. Percepción: detección, MOT, re-ID/MTMC, persistencia y actualización correcta del Core.
